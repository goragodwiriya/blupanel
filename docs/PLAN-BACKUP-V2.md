## 1. ทำไมต้องรื้อ

ระบบเดิมสร้างมาสำหรับคำถาม *"ผู้ดูแลเครื่องจะกู้เครื่องคืนยังไง"* แต่คำถามจริงที่ต้องตอบคือ
*"ลูกค้าจะเอาข้อมูลตัวเองคืนยังไง"* — สองอย่างนี้ต้องการคนละระบบ และการพยายามให้ระบบเดียว
ตอบทั้งสองคำถามคือที่มาของความซับซ้อนทั้งหมดที่เจอ:

| อาการที่เจอจริง | ต้นเหตุเชิงออกแบบ |
|---|---|
| ไฟล์สำรองอยู่ที่ `/var/lib/phpcp/backups` ซึ่ง `SelfProtection` กันไว้ทั้งก้อน | ที่เก็บอยู่ในพื้นที่ของ panel ไม่ใช่ของเจ้าของข้อมูล |
| ต้องเจาะข้อยกเว้นใน `SelfProtection` เพื่อให้เปิดดูได้ (เกือบเป็นรูโหว่ `..`) | ผลพวงจากข้อบน |
| ลูกค้าดาวน์โหลดสำเนาตัวเองไม่ได้เลย | ไฟล์ไม่ได้อยู่ในบ้านเขา |
| ขนาดไฟล์สำรองไม่นับในโควตาใคร | ลูกค้าสร้างได้ไม่จำกัดโดยไม่มีต้นทุน |
| หน้า Backups มีสี่ส่วน (ตารางเวลา · ปลายทาง · นำเข้า · รายการ) | ทุกความสามารถถูกวางเรียงกันหมดบนหน้าเดียว |
| ต้องมี `backup.import` เพื่อให้สำเนานอกเครื่องอ่านกลับได้ | แถวในตาราง `backups` เป็นแหล่งความจริง ไม่ใช่ตัวไฟล์ |

## 3. รูปทรงใหม่

```
/home/<user>/
  public_html/          ไฟล์เว็บ (เลย์เอาต์ cpanel ตามเดิม)
  logs/<domain>/
  backup/               ← ใหม่ · นับในโควตา · SFTP + ตัวจัดการไฟล์เข้าถึงได้อยู่แล้ว
    <domain>-files-20260814-030000.tar.gz
    <domain>-files-20260814-030000.tar.gz  ← มี backup.json อยู่ข้างใน
```

## 4. งานที่ต้องทำ — **เสร็จแล้วทั้งหมด**

### 4.1 ที่เก็บย้ายเข้าบ้าน ✔
- `SiteLayout::backupDir($home)` คืน `<บ้าน>/backup` · **ไม่รับชื่อโดเมนแล้ว** เพราะเป็น
  โฟลเดอร์ของบัญชี ไม่ใช่ของเว็บ (ชื่อโดเมนอยู่ในชื่อไฟล์) · เหมือนกันทั้งสองเลย์เอาต์
  จึงไม่ต้องย้ายอะไรตอนสลับเลย์เอาต์ — ซึ่งเป็นการย้ายที่ชนกันเองเมื่อบัญชีมีหลายเว็บ
- `BackupManager` ไม่มี "ไดเรกทอรีของระบบ" อีกแล้ว · ทุกเมธอดที่เขียนไฟล์รับ `Site`
  แล้วเขียนลง `$site->backupDir()` — เรียกให้เขียนออกนอกบ้านเจ้าของไม่ได้แม้ผู้เรียกพลาด
- **chown ไฟล์ที่สร้างให้เจ้าของ + chmod 0640** — ข้อนี้ไม่ได้อยู่ในแผนเดิมแต่ขาดไม่ได้:
  agent เป็น root ไฟล์ที่ tar สร้างจึงเป็น root:root 0600 ลูกค้าดาวน์โหลดไม่ได้เลย
- ตรวจโควตาก่อนสร้าง พร้อมบอกว่าใช้ไปเท่าไรจากเท่าไร (`BackupCapability::assertQuotaAllows`)
- ถอน `SelfProtection::allowAlso()` **ทั้งกลไก** · ถอนขอบเขต `backups` ใน `FileRoots` ·
  ถอน `Paths::useBackupsDir()`/`backupsDir()` — การกันพื้นที่ของ panel กลับไปไม่มีเงื่อนไข

### 4.2 ตัดของที่ไม่ใช้ ✔
- `BackupManager::TYPES` เหลือ `site`, `database` · `backupConfig()` ถูกลบ
- ตาราง `backups` เลิกเป็นแหล่งความจริง — ไม่มีที่ไหนเขียนแถวลงไปอีกแล้ว
  (`BackupCreate`, `BackupImport`, `DbDrop` เลิกบันทึก) · รายการอ่านจากโฟลเดอร์จริง
  ผ่าน `backup.list` → {@see \Phpcp\Domain\BackupFiles}
- ตารางเวลาหลายชุด → **`backup.auto` ตัวเดียว** ที่เรียก `backup.run` (รอบของทั้งเครื่อง)
  · `/api/v2/backup-schedules` (พหูพจน์ CRUD) → `/api/v2/backup-schedule` (เอกพจน์)
- ปลายทางหลายชุด → ชุดเดียว (`store()` ปฏิเสธการเพิ่มชุดที่สอง แก้ของเดิมได้เสมอ)
- **`backup.prune` ถูกถอดออกจากงานตั้งต้น** — ของเดิมเปิดไว้ตั้งแต่ติดตั้งและลบได้แต่
  ของที่ panel สร้างเอง · ถ้าคงไว้ มันจะกลายเป็นการลบไฟล์ในบ้านลูกค้าทุกตี 5 โดยที่
  ไม่มีใครสั่ง · ตอนนี้การเก็บกวาดเป็นขั้นตอนหนึ่งในรอบที่ผู้ดูแลเปิดเอง

### 4.3 ฐานข้อมูลเป็น .sql.gz ✔
- `MariaDbManager::dump()` บีบด้วย zlib ในโปรเซส (ไม่ต่อท่อ เพราะ `exec()` รับ argv ล้วน
  ไม่มี shell) และ **ปฏิเสธชื่อไฟล์ที่ไม่ลงท้ายด้วย `.gz`** เพื่อไม่ให้มีไฟล์บีบอัดที่
  ใช้ชื่อ `.sql`

### 4.4 ตารางเลือกบัญชี ✔
- migration `0022_backup_targets` เพิ่ม `users.backup_files`, `users.backup_database`
  (ค่าเริ่มต้น 0 ทั้งคู่)
- `GET/PATCH /api/v2/backup-targets` + ตารางช่องติ๊กในหน้า Backups (บันทึกทันทีที่ติ๊ก
  · ล้มแล้วติ๊กกลับให้ตรงกับความจริงบนเซิร์ฟเวอร์)

### 4.5 กู้คืนจากโฟลเดอร์ตัวเอง ✔
- `backup.restore` รับ `site_id` + `file` (ชื่อไฟล์ล้วน) แทน `backup_id`
- checksum คำนวณจากไฟล์เดี๋ยวนั้น ไม่ใช่อ่านจากตาราง
- **เพิ่มด่านที่แผนเดิมไม่ได้ระบุ:** อ่าน `backup.json` ยืนยันว่าไฟล์เป็นของเว็บนั้นจริง
  ก่อนแตกทับ — โฟลเดอร์เป็นของลูกค้า เขาเปลี่ยนชื่อไฟล์เองได้ ชื่อจึงไม่ใช่คำสัญญา
- ยังพิมพ์ชื่อโดเมนยืนยัน และ chown หลังแตกไฟล์เหมือนเดิม

## 6. กติกาของโปรเจกต์ที่ทำให้เสียเวลาไปแล้ว

- **`meta.*` ผูกกับ `data-text`/`data-if` ไม่ได้** — คอมโพเนนต์เห็นเฉพาะชั้น `data`
- **`requestApi` ไม่เรียก `ResponseHandler.process()`** — คำสั่งจากเซิร์ฟเวอร์ถูกทิ้งทั้งหมด
  ปุ่มที่เปลี่ยนข้อมูลต้องใช้ `apiRefresh` หรือเขียน action เองใน `js/ui.js`
- **`GraphComponent` วาด `data.slice(0, maxDataPoints)`** — จุด*แรก* ไม่ใช่จุดล่าสุด
- **แก้ capability แล้วต้อง `systemctl restart phpcp-agentd`** ไม่งั้นรันโค้ดเก่าเงียบ ๆ
- **แก้ไฟล์ใน `vendor/now/` แล้วต้องอัปเดต `SHA256SUMS`**
  `cd public/assets/spa/vendor/now && awk '{print $2}' SHA256SUMS | xargs -d '\n' sha256sum > SHA256SUMS.new && mv SHA256SUMS.new SHA256SUMS`
- **`php tests/run.php` ต้องผ่านครบก่อน commit** (ตอนนี้ 790 ข้อ)
- **ย้อนบั๊กกลับเข้าไปพิสูจน์ว่าเทสต์จับได้จริง** ก่อน commit ทุกครั้ง

## 7. สิ่งที่ต่างจากแผน และสิ่งที่ยังเหลือ

### ต่างจากแผน (ตัดสินระหว่างทำ)

| เรื่อง | แผนเดิม | ที่ทำจริง | เหตุผล |
|---|---|---|---|
| `backupDir()` | เปลี่ยนเฉพาะเลย์เอาต์ cpanel | เปลี่ยนทั้งสองเลย์เอาต์ | ถ้าเปลี่ยนข้างเดียว การย้ายเลย์เอาต์ของบัญชีที่มีหลายเว็บจะชนกันเอง (หลายต้นทาง → ปลายทางเดียว) |
| ชื่อไฟล์ฐานข้อมูล | `<โดเมน>-db-<เวลา>` | `<โดเมน>-db-<ชื่อฐาน>-<เวลา>` | เว็บหนึ่งมีได้หลายฐาน · ไฟล์ที่แยกไม่ออกว่าเป็นฐานไหนคือไฟล์ที่ลูกค้าต้องเดาตอนกู้คืน |
| รายการไฟล์ | ไม่ได้ระบุว่าใครอ่าน | อ่านผ่าน agent (`backup.list`) | โฟลเดอร์เป็นของลูกค้าโหมด 0750 · โปรเซสเว็บอ่านไม่ได้ตามที่ SECURITY ตั้งใจ · agent ล่ม = 503 ไม่ใช่ "ไม่มีไฟล์" |
| เจ้าของไฟล์ | ไม่ได้ระบุ | chown + chmod 0640 ทุกไฟล์ที่สร้าง | ไม่ทำ = ลูกค้าเห็นไฟล์แต่ดาวน์โหลดไม่ได้ ซึ่งล้มเป้าหมายทั้งหมดเงียบ ๆ |
| ลบสำเนานอกเครื่อง | ไม่ได้ระบุ | ลบตามไฟล์ในเครื่อง โดยคำนวณชื่อ `<บัญชี>-<ไฟล์>` | ไม่มีตารางจำแล้ว · ปลายทางไม่มี API ไล่รายการไฟล์ ไฟล์ที่ลูกค้าลบเองก่อนจึงค้างที่ปลายทาง (รับรู้ไว้) |

### เจอจากการทดสอบบนเครื่องจริง (ไม่ใช่จากเทสต์)

1. **tar หาใบแจ้งข้อมูลไม่เจอ** — `--directory dirname($manifest)` ส่งเส้นทางเชิงตรรกะ
   ไปให้คำสั่งจริงโดยไม่ผ่าน `$executor->path()` · ทั้งคำสั่งล้มในโหมด sandbox
2. **เศษไฟล์ค้างเมื่อ tar ล้ม** — tar สร้างไฟล์ปลายทางตั้งแต่วินาทีแรก · ล้มกลางทาง
   เหลือ `.tar.gz` 20 ไบต์ในโฟลเดอร์ลูกค้า ซึ่ง**โผล่ในรายการพร้อมปุ่มกู้คืน**
   ตอนนี้ลบทิ้งเมื่อล้มแล้ว

### ยังเหลือ

- **migration ลบตาราง `backups`** — ยังไม่ลบตามที่แผนบอกไว้ ("ลบทีหลังเมื่อแน่ใจ")
- **การกู้คืนฐานข้อมูล** ยังไม่เปิด · ลูกค้าดาวน์โหลด `.sql.gz` ไปนำเข้าเองผ่าน phpMyAdmin
- **ไฟล์เก่าที่ยังอยู่ `/var/lib/phpcp/backups`** ของการติดตั้งเดิมไม่ถูกย้ายให้อัตโนมัติ
  · ผู้ดูแลต้องย้ายเข้าบ้านของเจ้าของเองถ้ายังต้องการใช้ (ไม่มีอะไรอ่านมันแล้ว)
