> **สถานะเอกสาร:** ข้อเสนอที่ตกลงขอบเขตแล้ว · เขียนเมื่อ 2026-08-14
> **เอกสารนี้กลับคำตัดสินของ** [PLAN-V2.md](PLAN-V2.md) เฟส E1 ที่ออกแบบให้ไฟล์สำรอง
> เป็นทรัพยากรของ **ผู้ดูแลเครื่อง** เก็บรวมไว้ที่ `/var/lib/phpcp/backups`
> **เอกสารประกอบ:** [ARCHITECTURE.md](ARCHITECTURE.md) · [SECURITY.md](SECURITY.md)
>
> **เป้าหมาย:** ไฟล์สำรองเป็น**ของลูกค้า อยู่ในบ้านของลูกค้า** — ดาวน์โหลดเองได้ผ่าน
> SFTP/ตัวจัดการไฟล์ นับในโควตาของตัวเอง และกู้คืนได้จากไฟล์ของตัวเองเท่านั้น

## 1. ทำไมต้องรื้อ

ระบบเดิมสร้างมาสำหรับคำถาม *"ผู้ดูแลเครื่องจะกู้เครื่องคืนยังไง"* แต่คำถามจริงที่ต้องตอบคือ
*"ลูกค้าจะเอาข้อมูลตัวเองคืนยังไง"* — สองอย่างนี้ต้องการคนละระบบ และการพยายามให้ระบบเดียว
ตอบทั้งสองคำถามคือที่มาของความซับซ้อนทั้งหมดที่เจอ:

| อาการที่เจอจริง | ต้นเหตุเชิงออกแบบ |
|---|---|
| ไฟล์สำรองอยู่ที่ `/var/lib/phpcp/backups` ซึ่ง `SelfProtection` กันไว้ทั้งก้อน | ที่เก็บอยู่ในพื้นที่ของ panel ไม่ใช่ของเจ้าของข้อมูล |
| ต้องเจาะข้อยกเว้นใน `SelfProtection` เพื่อให้เปิดดูได้ (เกือบเป็นรูโหว่ `..`) | ผลพวงจากข้อบน |
| ลูกค้าดาวน์โหลดสำเนาตัวเองไม่ได้เลย | ไฟล์ไม่ได้อยู่ในบ้านเขา |
| ขนาดไฟล์สำรองไม่นับในโควตาใคร | ลูกค้าสร้างได้ไม่จำกัดโดยไม่มีต้นทุน |
| หน้า Backups มีสี่ส่วน (ตารางเวลา · ปลายทาง · นำเข้า · รายการ) | ทุกความสามารถถูกวางเรียงกันหมดบนหน้าเดียว |
| ต้องมี `backup.import` เพื่อให้สำเนานอกเครื่องอ่านกลับได้ | แถวในตาราง `backups` เป็นแหล่งความจริง ไม่ใช่ตัวไฟล์ |

## 3. รูปทรงใหม่

```
/home/<user>/
  public_html/          ไฟล์เว็บ (เลย์เอาต์ cpanel ตามเดิม)
  logs/<domain>/
  backup/               ← ใหม่ · นับในโควตา · SFTP + ตัวจัดการไฟล์เข้าถึงได้อยู่แล้ว
    <domain>-files-20260814-030000.tar.gz
    <domain>-files-20260814-030000.tar.gz  ← มี backup.json อยู่ข้างใน
    <domain>-db-20260814-030000.sql.gz
```

`SiteLayout::requiredDirectories()` เพิ่ม `backup/` เข้าไป และ `SiteProvisioner::ownershipTargets()`
ต้องครอบมันด้วย ไม่งั้นลูกค้าเขียน/ลบไฟล์ของตัวเองไม่ได้ (บทเรียนเดิมจาก `logs/`)

## 4. งานที่ต้องทำ

### 4.1 ที่เก็บย้ายเข้าบ้าน
- `SiteLayout` เพิ่ม `backupDir()` ที่ชี้ `<บ้าน>/backup` สำหรับเลย์เอาต์ cpanel
  (ตอนนี้ชี้ `<บ้าน>/backups/<domain>` ซึ่งไม่ตรงกับที่ตกลง)
- `BackupManager` เขียนไฟล์ลงบ้านของเจ้าของ ไม่ใช่ `Paths::backups()`
- ตรวจโควตาก่อนสร้าง — เต็มแล้วต้องปฏิเสธพร้อมบอกว่าเหลือเท่าไร ไม่ใช่เขียนจนดิสก์เต็ม
- **ถอน `SelfProtection::allowAlso()` และขอบเขต `backups` ใน `FileRoots`** ที่เพิ่งเพิ่มไป
  (commit `dc4425e`) — ไม่ต้องมีช่องว่างใน CP อีกแล้ว รวมถึง `Paths::useBackupsDir()`

### 4.2 ตัดของที่ไม่ใช้
- `backup.create` ชนิด `config` และ `full` → เอาออก (B2)
- `BackupManager::backupConfig()` → เอาออก
- ตาราง `backups` → เลิกใช้เป็นแหล่งความจริง (migration ลบทีหลังเมื่อแน่ใจ)
- `backup-schedules` หลายชุด → เหลือ cron ตัวเดียว
- ปลายทางหลายชุด → เหลือชุดเดียว

### 4.3 ฐานข้อมูลเป็น .sql.gz
- `MariaDbManager::dump()` ต่อท่อผ่าน gzip · ตอนนี้ได้ `.sql` ดิบ

### 4.4 ตารางเลือกบัญชี
- คอลัมน์ใหม่ใน `users`: `backup_files` · `backup_database` (ค่าเริ่มต้น 0 ตาม B7)
- เส้นทาง `GET/PATCH /api/v2/backup-targets`

### 4.5 กู้คืนจากโฟลเดอร์ตัวเอง
- `backup.restore` รับ**ชื่อไฟล์ในโฟลเดอร์ของตัวเอง** แทน `backup_id`
- ยังต้องพิมพ์ชื่อโดเมนยืนยัน และ chown หลังแตกไฟล์ (commit `b6dd06a`)

## 6. กติกาของโปรเจกต์ที่ทำให้เสียเวลาไปแล้ว

- **`meta.*` ผูกกับ `data-text`/`data-if` ไม่ได้** — คอมโพเนนต์เห็นเฉพาะชั้น `data`
- **`requestApi` ไม่เรียก `ResponseHandler.process()`** — คำสั่งจากเซิร์ฟเวอร์ถูกทิ้งทั้งหมด
  ปุ่มที่เปลี่ยนข้อมูลต้องใช้ `apiRefresh` หรือเขียน action เองใน `js/ui.js`
- **`GraphComponent` วาด `data.slice(0, maxDataPoints)`** — จุด*แรก* ไม่ใช่จุดล่าสุด
- **แก้ capability แล้วต้อง `systemctl restart phpcp-agentd`** ไม่งั้นรันโค้ดเก่าเงียบ ๆ
- **แก้ไฟล์ใน `vendor/now/` แล้วต้องอัปเดต `SHA256SUMS`**
  `cd public/assets/spa/vendor/now && awk '{print $2}' SHA256SUMS | xargs -d '\n' sha256sum > SHA256SUMS.new && mv SHA256SUMS.new SHA256SUMS`
- **`php tests/run.php` ต้องผ่านครบก่อน commit** (ตอนนี้ 774 ข้อ)
- **ย้อนบั๊กกลับเข้าไปพิสูจน์ว่าเทสต์จับได้จริง** ก่อน commit ทุกครั้ง
